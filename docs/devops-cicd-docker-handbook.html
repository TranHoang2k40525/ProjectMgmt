Vì sao không ghi connection string thật trong class library?

Domain, Application và Infrastructure là code có thể được tái sử dụng ở nhiều môi trường. Nếu class library giữ password, DLL nào cũng mang theo secret và mỗi lần đổi database bạn phải build lại code. Host ProjectMgmt.Solution mới là nơi quyết định môi trường và truyền cấu hình cho các DbContext qua DI.

Thứ tự ghi đè cần nhớ

ASP.NET Core nạp cấu hình từ file chung, file theo môi trường, User Secrets trong Development, biến môi trường và tham số dòng lệnh. Nguồn đến sau có thể ghi đè nguồn trước. Vì vậy ConnectionStrings__ProjectMgmt có thể ghi đè ConnectionStrings:ProjectMgmt mà không sửa file. Hai dấu gạch dưới được dùng vì dấu hai chấm không thuận tiện trên mọi hệ điều hành.

  • Không in connection string vào log và không gửi nó trong chat/issue/PR.

Cách thêm một key cấu hình mới

  1. Thêm giá trị mặc định không nhạy cảm vào appsettings.json.
  2. Thêm giá trị môi trường vào các file *.example.json.
  3. Cập nhật file thật ở máy TEST, không commit file thật.
  4. Đọc key qua builder.Configuration["Section:Key"] hoặc Options pattern.
  5. Thêm kiểm tra fail-fast nếu key là bắt buộc.
  6. Cập nhật tài liệu và chạy CI.

6. Docker và Compose trong dự án này

Vì sao dùng multi-stage build?

Image dùng để build cần SDK, compiler và npm; image chạy thật chỉ cần runtime hoặc Nginx. Multi-stage build tách hai việc này. Kết quả là image cuối nhỏ hơn, ít công cụ thừa hơn và giảm bề mặt tấn công.

API Dockerfile làm gì?

  1. Dùng mcr.microsoft.com/dotnet/sdk:10.0 để restore và publish.
  2. Copy các *.csproj trước để Docker cache lớp restore.
  3. Copy source sau; đổi một file .cs không buộc tải lại toàn bộ NuGet package.
  4. Publish Release với UseAppHost=false.
  5. Chỉ copy output sang image runtime aspnet:10.0.
  6. Chạy bằng user không phải root và nghe cổng nội bộ 8080.
  7. Cài curl để health check gọi /health/live.
Khi thêm một class library mới được API tham chiếu, hãy thêm dòng COPY cho file .csproj đó vào lớp restore của API Dockerfile. Nếu quên, container-ci sẽ báo lỗi restore/build.

Web Dockerfile làm gì?

  1. Dùng Node 24 để chạy npm ci và production build Angular.
  2. Chỉ copy thư mục dist/projectmgmt-web/browser sang Nginx.
  3. Nginx chạy cổng 8080 không đặc quyền.
  4. try_files ... /index.html giúp refresh route Angular không bị 404.
  5. /api và /hubs được proxy sang service có tên api.

9. Hiểu CI của ProjectMgmt

CI nằm tại .github/workflows/ci.yml, chạy khi có pull request vào develop hoặc khi bấm Run workflow. Các job độc lập nên GitHub có thể chạy song song.

backend-ci

  1. Checkout đúng commit của PR.
  2. Cài .NET SDK 10.
  3. dotnet restore ProjectMgmt.slnx.
  4. Build Release với --no-restore.
  5. Chạy project test với --no-build.

Việc tách restore/build/test giúp biết lỗi nằm ở giai đoạn nào và tránh thực hiện cùng một việc nhiều lần.

frontend-ci

  1. Cài Node 24 và dùng cache npm.
  2. npm ci cài đúng lockfile, không tự ý cập nhật phiên bản.
  3. ESLint kiểm tra quy tắc TypeScript/HTML.
  4. Vitest chạy unit test không bật watch.
  5. Angular production build xác nhận code có thể đóng gói.

container-ci

  1. Kiểm tra cả local Compose và TEST Compose bằng docker compose config --quiet.
  2. Khởi tạo Docker Buildx.
  3. Build API image, không push registry.
  4. Build web image, không push registry.
  5. Dùng GitHub Actions cache riêng cho từng image.
Ba job có tên duy nhất và đều là required checks của develop. Một job đỏ thì PR không được merge.

CI không làm gì?

  • Không dùng connection string TEST.
  • Không kết nối Aiven.
  • Không sửa IIS.
  • Không deploy.
  • Hiện chưa push image lên GHCR; container-ci mới xác minh khả năng build.

Vì sao cần self-hosted runner?

GitHub-hosted runner ở ngoài máy của bạn nên không thể an toàn ghi trực tiếp vào thư mục IIS local. Self-hosted runner là dịch vụ chạy ngay trên máy TEST, có quyền tối thiểu với thư mục deploy, config, log và backup. Đổi lại, bạn phải tự cập nhật Windows, runtime và bảo vệ máy này.

12. Database, schema và migration

Hai nguồn thay đổi schema

  • Database-first: SQL/database là nguồn đúng; reverse engineering cập nhật entity/configuration.
  • Code-first: Entity/configuration là nguồn đúng; EF migration cập nhật database.
Không trộn hai hướng trong cùng một thay đổi mà không so sánh kỹ. Nếu sửa SQL thủ công rồi lại tạo migration từ model cũ, EF có thể cố tạo lại hoặc xóa đối tượng không đúng ý.

Ba DbContext của modular monolith

  • IdentityExperienceDbContext
  • PlanningDbContext
  • DeliveryIntelligenceDbContext

Mỗi context có migration history table riêng để ba module không tranh cùng một lịch sử. Các module vẫn dùng chung một database vật lý nhưng ownership của model và migration được tách rõ.

Quy trình migration an toàn

  1. Tạo backup database TEST.
  2. Chọn đúng DbContext và đúng project migrations.
  3. Tạo migration với tên mô tả nghiệp vụ.
  4. Đọc cả phương thức Up và Down.
  5. Xuất SQL idempotent hoặc migration bundle để review.
  6. Thử trên database local/clone TEST.
  7. Chỉ áp dụng TEST khi đã kiểm tra dữ liệu.
  8. Ứng dụng chạy bằng tài khoản DB ít quyền; tài khoản migration nên tách riêng.
# Ví dụ khung lệnh; thay <Context> và đường dẫn project đúng module
dotnet ef migrations add <TenMigration> \
  --context <Context> \
  --project <Infrastructure.csproj> \
  --startup-project ProjectMgmt.Solution/ProjectMgmt.Solution.csproj

dotnet ef migrations script --idempotent \
  --context <Context> \
  --project <Infrastructure.csproj> \
  --startup-project ProjectMgmt.Solution/ProjectMgmt.Solution.csproj

CD hiện tại cố ý không tự chạy migration. Lý do: migration có thể khóa bảng, mất dữ liệu hoặc cần review SQL. Khi hệ thống trưởng thành, có thể thêm một job migration riêng có approval trước job deploy.

13. Cách viết, sửa và mở rộng hệ thống

Thêm một module/project mới

  1. Tạo Domain, Application và Infrastructure đúng ranh giới module.
  2. Thêm project vào solution và khai báo ProjectReference đúng chiều.
  3. Thêm DI ở Program.cs theo chủ trương hiện tại.
  4. Thêm dòng COPY csproj vào API Dockerfile nếu API tham chiếu project mới.
  5. Nếu có DbContext mới, chọn migration history table riêng.
  6. Build solution, build Docker và cập nhật tài liệu.

Thêm NuGet package

  1. Khai báo version một lần trong Directory.Packages.props.
  2. Chỉ thêm PackageReference vào project thực sự dùng package.
  3. Không thêm cùng package vào Contracts/Core/Test chỉ để “cho chắc”.
  4. Restore, build, test và kiểm tra license/security advisory.

Thêm npm package

cd frontend/projectmgmt-web
npm install <package>
npm run lint
npm test -- --watch=false
npm run build

Commit cả package.json và package-lock.json. CI dùng npm ci, nên hai file lệch nhau sẽ làm pipeline dừng ngay.

Thêm endpoint

  1. DTO đầu vào/đầu ra ở Application.
  2. Interface service và implementation xử lý use case.
  3. Repository interface ở tầng trong; implementation ở Infrastructure.
  4. Controller chỉ nhận request, gọi service và trả HTTP response.
  5. Đăng ký interface/implementation trong DI.
  6. Thêm test ít nhất cho happy path, validation và lỗi.

Thay health check

/health/live chỉ nên trả lời tiến trình còn sống. /health có thể kiểm tra readiness như DB. Không dùng một readiness check quá nặng mỗi vài giây vì chính health check có thể tạo tải cho database.

14. Bảo trì và nâng cấp

Hằng tuần

  • Xem runner còn online và ổ đĩa còn đủ chỗ.
  • Đọc các workflow thất bại, không rerun mù nhiều lần.
  • Kiểm tra log deploy và backup mới nhất.
  • Kiểm tra package có security advisory.

Hằng tháng

  • Cập nhật Windows, IIS Hosting Bundle và Docker Desktop nếu được dùng.
  • Kiểm tra dung lượng C:\DeployBackup\ProjectMgmt-Test và C:\Logs\ProjectMgmt.

Nâng .NET

  4. Đổi setup-dotnet
  5. Cài Hosting Bundle tương ứng trên IIS trước khi deploy.
  6. Chạy test và smoke test trên TEST trước Production.

Nâng Angular/Node

  2. Cập nhật Node trong web Dockerfile và setup-node cùng lúc.
  3. Tạo lại lockfile bằng npm version đã khai báo.
  4. Chạy lint, unit test, build và container-ci.

Nâng MySQL image

Backup volume trước. Đọc release notes, thử trên bản sao dữ liệu và không đổi lower_case_table_names trên data directory đã khởi tạo. Giá trị này cần được quyết định trước lần tạo volume đầu tiên.

15. Vận hành và xử lý sự cố

CI backend đỏ

  1. Mở job backend-ci, tìm bước đầu tiên đỏ.
  2. Nếu restore lỗi: kiểm tra package/version/network.
  3. Nếu build lỗi: đọc file, dòng và mã lỗi CSxxxx.
  4. Nếu test lỗi: chạy đúng lệnh test ở local, không sửa workflow để bỏ test.

CI frontend đỏ

  • npm ci lỗi: package.json và lockfile có thể lệch.
  • Lint lỗi: sửa đúng file/dòng ESLint báo.
  • Test lỗi: đọc assertion và chạy test riêng.
  • Build lỗi: kiểm tra TypeScript, budget và environment replacement.

container-ci đỏ

  • Compose config lỗi: biến bắt buộc thiếu hoặc YAML sai.
  • API restore lỗi: Dockerfile thiếu COPY cho một csproj mới.
  • Web build lỗi: lockfile hoặc đường dẫn output Angular thay đổi.
  • Pull image lỗi: registry/tag không tồn tại hoặc GitHub bị giới hạn mạng.

CD không bắt đầu

  • Xác nhận commit đã vào develop, không chỉ nằm ở hoangtv.
  • Xem runner có online và đủ bốn nhãn.
  • Xem job có đang chờ Environment approval hay concurrency không.
  • Kiểm tra dịch vụ Windows của runner.

CD rollback

Đọc C:\Logs\ProjectMgmt\deploy-test.log. Tìm health attempt đầu tiên và thông báo rollback. Không xóa backup trước khi biết phiên bản cũ đã chạy lại. Backup nằm tại C:\DeployBackup\ProjectMgmt-Test.

IIS trả 500

  1. Kiểm tra Hosting Bundle/ANCM V2 và app pool “No Managed Code”.
  2. Kiểm tra ASPNETCORE_ENVIRONMENT=Staging.
  3. Kiểm tra file Staging thật có trong thư mục publish và runner đọc được.
  4. Xem Windows Event Viewer và stdout log tạm thời nếu cần.
  5. Không bật stdout logging lâu dài vì có thể đầy ổ đĩa và lộ dữ liệu.

Không kết nối được Aiven

  • Kiểm tra host, port, user, database và password đã xoay.
  • Kiểm tra SslMode=Required.
  • Kiểm tra firewall/network từ chính máy runner.
  • Không in nguyên connection string khi chẩn đoán.

Lệnh Docker thường dùng khi có sự cố

docker compose --env-file .env ps
docker compose --env-file .env logs --tail 200 api
docker compose --env-file .env logs --tail 200 web
docker compose --env-file .env logs --tail 200 mysql
docker compose --env-file .env restart api

16. Lộ trình DevOps/CI/CD nâng cao

Cấp 1 - Hiểu và vận hành được hệ thống hiện tại

  • Đọc Git diff và biết file nào được stage.
  • Hiểu PR, required checks, artifact và runner.
  • Chạy Compose local, đọc log và phân biệt image/container/volume.
  • Biết secret nằm ở đâu và vì sao không được commit.

Cấp 2 - Tăng chất lượng

  • Viết integration test dùng Testcontainers hoặc database tạm.
  • Thêm CodeQL/SAST, dependency review và secret scanning.
  • Quét image bằng Trivy hoặc Docker Scout.
  • Tạo SBOM và ký image/artifact.
  • Dùng Dependabot/Renovate nhưng vẫn review nâng version.

Cấp 3 - Phát hành container

  • Đăng nhập GHCR bằng GITHUB_TOKEN.
  • Tag image theo commit SHA và semantic version; không chỉ dùng latest.
  • Push image chỉ sau khi CI xanh.
  • CD kéo đúng digest để bảo đảm image chạy là image đã kiểm tra.
  • Giữ IIS CD hoặc container CD cho một môi trường, không để hai luồng tranh nhau.

Cấp 4 - Triển khai an toàn hơn

  • Thêm approval cho Production environment.
  • Blue/green hoặc canary để giảm downtime.
  • Migration job riêng có backup và approval.
  • Centralized logs, metrics, traces và cảnh báo.
  • Định nghĩa SLO: tỷ lệ thành công, latency, thời gian phục hồi.

Cấp 5 - Hạ tầng dưới dạng code

  • Dùng Terraform/Bicep/Ansible cho máy, network, IIS hoặc cloud.
  • Dùng secret manager thay file tĩnh khi quy mô tăng.
  • Tạo môi trường tạm cho từng PR.
  • Dùng OIDC thay credential cloud sống lâu.

18. Checklist thực hành

Trước khi mở/cập nhật PR

  • git status chỉ có file mình định thay đổi.
  • Không có password, token, private key hoặc connection string thật.
  • Solution build thành công.
  • Frontend lint/test/build thành công nếu có ảnh hưởng.
  • Compose config thành công nếu sửa Docker.
  • Migration đã được đọc và thử nếu có.
  • Commit message nói rõ mục đích.

Trước khi merge vào develop

  • PR diff đã được review.
  • backend-ci xanh.
  • frontend-ci xanh.
  • container-ci xanh.
  • File Staging thật tồn tại và không còn placeholder.
  • Runner TEST online.
  • Đã biết người theo dõi deployment.

Sau khi merge

  • Workflow Deploy TEST đã bắt đầu.
  • Build artifacts thành công.
  • Self-hosted runner nhận job.
  • Health check HTTP 2xx.
  • Smoke test đăng nhập/API chính.
  • Kiểm tra log không có lỗi mới.
  • Ghi báo cáo release.

Khi rollback

  • Dừng thay đổi tiếp theo.
  • Giữ log và artifact của lần lỗi.
  • Xác nhận backup nào được phục hồi.
  • Kiểm tra health và nghiệp vụ sau rollback.
  • Viết nguyên nhân gốc, không chỉ ghi “deploy lỗi”.
  • Tạo issue/hành động phòng ngừa tái diễn.
